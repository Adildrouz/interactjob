# InteractJob.ma — Estimated Hours Invested (2026-05-10 → 2026-07-27)

Evidence-based estimate built from full git commit history across every branch and both
related repositories. Methodology, numbers, and honest caveats below — **read the caveats
section before treating the headline number as final.**

## Headline estimate

| Session gap threshold | Sessions | Total hours |
|---|---|---|
| 60 min | 162 | **131.1 h** |
| **90 min (primary)** | **143** | **148.1 h** |
| 120 min | 130 | **166.0 h** |

**Primary estimate: ~148 hours over 78.7 days (11.2 weeks).** That's an average of ~13.2
hours/week, but activity was very uneven (see weekly table) — this is a floor, not a ceiling
(see Caveats).

Why three thresholds: a "session" is a run of commits close enough together to plausibly be
one continuous sitting. A tighter gap (60 min) splits borderline cases into more, shorter
sessions; a looser gap (120 min) merges them into fewer, longer ones. The true number is
somewhere in this range — 90 min is used as the primary estimate because it's the middle
ground and matches how this project actually seems to work (edit → test → fix in a loop,
often with 30-70 min gaps for builds/deploys/thinking between commits).

Each session's duration = (timestamp of last commit − timestamp of first commit) + a flat
**20-minute buffer** (time spent before the first commit and after the last one in a sitting —
reading, planning, verifying — that never shows up in git). A single-commit session still
gets the 20-minute buffer, nothing more.

## Commit classification

Not every commit represents work time. Commits were split into four kinds:

| Kind | Count | Counted toward hours? |
|---|---|---|
| **Dev work** (real feature/fix/refactor/seo/etc. commits) | 480 | ✅ Yes — this is what session clustering runs on |
| **Automated cron** (`[skip ci]` — LinkedIn dedup state, remote-jobs sync, scheduled agent data updates) | 2,718 | ❌ No — scheduled, unattended Railway agent runs, not owner activity |
| **Admin moderation** (`chore(admin): approve/reject/close job`) | 82 | ❌ No — single UI clicks in the admin dashboard, not coding sessions. Flagged, not deleted: real owner engagement, just not "hours of work" in the coding sense. |
| **Public submissions** (`chore(submit): new pending job`) | 68 | ❌ No — third-party recruiters using the public submission form, not the owner at all |

The 2,718 automated cron commits span the full window (first one 2026-05-16, still firing as
of 2026-07-27) at a roughly steady multi-times-per-day cadence — background infrastructure,
not development time, but the sheer count is worth knowing: this project runs a genuinely
active always-on agent, which itself represents real (earlier) engineering investment to build
and keep running, separate from the ongoing coding hours counted here.

## What this estimate does NOT capture (read this before quoting the headline number)

The real total is **very likely higher than 148 hours, not lower**. This method only measures
a floor:

1. **Chat time with no resulting commit.** Planning conversations, reviewing Claude's output,
   asking questions, deciding not to proceed with something — none of this leaves a git trace.
   Given how this project is actually built (Claude Code doing the typing), a meaningful chunk
   of "thinking and directing" time between commits is real work not counted here.
2. **Manual testing, browsing, and outreach time** — clicking through the live site, checking
   LinkedIn manually, any outreach/relationship work for recruiters — none of it touches git.
3. **Autonomous agent time counted as if it were owner attention.** Some sessions in this
   dataset may represent Claude Code working continuously while the owner was doing something
   else entirely (the session-duration method can't tell the difference between "actively
   watching every step" and "kicked it off and came back an hour later"). This could cut
   either way per session, but the aggregate effect is more likely to overstate *continuous
   attention* than overstate elapsed wall-clock time.
4. **Everything outside git**: Vercel/Railway dashboard configuration, environment variables,
   DNS, domain setup, LinkedIn Developer Portal / Buffer / PayPal app configuration, MongoDB
   Atlas setup, admin-password rotation, and the two production-secret incidents diagnosed this
   week (`MONGODB_URI_DEV` never existing in prod, `EMPLOYER_JWT_SECRET` missing) — real hours,
   zero git footprint.
5. **The 2,718 automated commits represent real earlier engineering investment** (building the
   always-on Railway agent, its cron scheduling, dedup logic, GitHub-sync pipeline) that shows
   up here only as "infrastructure exists," not as hours — the hours to build *that* system are
   folded into the dev-work sessions that created it, but its ongoing operation isn't "new" hours
   even though it required real work to reach that steady state.

**Bottom line: treat 148 hours (90-min threshold) as a defensible lower bound**, with 131-166 h
as the plausible range depending on session-gap assumption, and assume genuine total effort
(including everything in this section) is meaningfully above that.

## Methodology notes / reproducibility

- Raw data: `git log --all --pretty=format:"%H|%ai|%an|%s"` from both repos, deduped by commit
  hash, filtered to `>= 2026-05-10`, sorted chronologically into one master timeline.
- Worktrees were not queried separately — every branch checked out in a worktree is a normal
  local branch ref in the same repository, so `git log --all` in the primary checkout already
  includes all of it (confirmed: 53 branches, 20 active worktrees, zero additional commits found
  by checking any worktree individually).
- Session clustering, area categorization, and all aggregation done via a one-off Node script
  operating on the parsed log — not a persisted tool, but the logic is fully described above if
  it needs to be re-run later with different thresholds.
